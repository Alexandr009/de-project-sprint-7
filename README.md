# Проект 7-го спринта. Организация Data Lake

Геоаналитика соцсети: определение города события по координатам, витрины
в разрезе пользователей и зон, рекомендация друзей.

## Структура Data Lake

Хранилище наследует трёхслойную структуру, построенную в спринте, и
расширяется геоданными.

| Слой | Путь | Формат | Что лежит | Обновление |
|---|---|---|---|---|
| Raw | `/user/master/data/geo/events` | Parquet, партиции `date` | сырые события с координатами, как отгружает источник | ежедневно источником |
| Справочники | `/user/s19239739/data/geo/geo.csv` | CSV (`;`, дробная часть через запятую) | координаты центров 24 городов Австралии | по мере изменения |
| Аналитика | `/user/s19239739/data/analytics/<витрина>/date=<дата>` | Parquet, партиции `date` | готовые витрины | ежедневно, DAG `geo_marts` |
| Песочница | `/user/s19239739/data/tmp` | Parquet | отладочные расчёты, срезы для проверки гипотез | вручную |

Витрины в слое аналитики:

- `mart_users` — портрет пользователя: актуальный и домашний город, путешествия;
- `mart_zones` — активность по городам за неделю и месяц;
- `mart_friends` — пары для рекомендации друзей.

Каждая витрина партиционирована по дате расчёта, поэтому пересчёт одной даты
не затрагивает соседние партиции, а история расчётов сохраняется.

**Почему Raw остаётся в мастер-слое.** События с координатами приходят уже
партиционированными по дате, и перекладывать их в личный слой не требуется:
джобы читают их напрямую, а фильтр по дате опускается до чтения партиций.
Города и таймзоны добавляются на лету, а не материализуются отдельным слоем —
справочник маленький (24 строки) и рассылается бродкастом.

## Структура репозитория

```
src/
├── dags/
│   └── geo_marts_dag.py     # ежедневный расчёт трёх витрин
└── scripts/
    ├── geo_lib.py           # справочник городов, гаверсинус, привязка событий
    ├── mart_users.py        # витрина в разрезе пользователей
    ├── mart_zones.py        # витрина в разрезе зон
    └── mart_friends.py      # витрина рекомендации друзей
```

## Витрины

### mart_users

| Поле | Описание |
|---|---|
| `user_id` | идентификатор пользователя |
| `act_city` | город последнего сообщения |
| `home_city` | последний город, где пользователь пробыл дольше 27 дней |
| `travel_count` | количество посещений городов |
| `travel_array` | города в порядке посещения |
| `local_time` | время последнего события в таймзоне актуального города |

### mart_zones

| Поле | Описание |
|---|---|
| `month`, `week` | месяц и неделя расчёта |
| `zone_id` | идентификатор города |
| `week_message`, `week_reaction`, `week_subscription`, `week_user` | события за неделю |
| `month_message`, `month_reaction`, `month_subscription`, `month_user` | события за месяц |

### mart_friends

| Поле | Описание |
|---|---|
| `user_left`, `user_right` | пара пользователей, `user_left < user_right` |
| `processed_dttm` | дата расчёта витрины |
| `zone_id` | идентификатор города |
| `local_time` | локальное время в зоне |

## Принятые решения

**Определение города.** Расстояние от координат события до центра города
считается по формуле гаверсинуса, событие относится к ближайшему городу.
Справочник из 24 городов рассылается бродкастом, поэтому `crossJoin`
с ним не вызывает шаффла.

**Таймзоны.** В `geo.csv` таймзоны нет, а для `local_time` она нужна, поэтому
в `geo_lib.py` заведено соответствие «город → таймзона»: 24 города Австралии
распределены по шести зонам.

**Хронология событий.** У личных сообщений год в `event.message_ts` сдвинут
на единицу относительно партиции (`2021-05-25` при `date=2022-05-25`), поэтому
порядок событий строится по колонке `date`, а timestamp используется только
для времени суток в `local_time`.

**Домашний город.** Считается непрерывная серия сообщений из одного города;
её длительность — разница между первым и последним днём серии включительно.
Домашним считается город последней серии длиннее 27 дней, то есть 28
календарных дней и более. Альтернативный критерий «все сообщения только из
этого города» отбрасывает почти всех: координаты в данных распределены
случайно, поэтому пользователи ежедневно «перемещаются» между городами, и на
всю историю приходится 312 тысяч визитов при 125 тысячах пользователей.
Из-за этого `home_city` заполнен примерно у 17 тысяч пользователей — у самых
активных непрерывной серии в 28 дней просто не набирается.

**Путешествия.** `travel_count` — число визитов, а не уникальных городов:
повторный приезд считается отдельным посещением, как требует задание.

**Зона для событий без координат.** Координаты есть только у сообщений,
поэтому реакции, подписки и регистрации относятся к городу последнего
сообщения того же пользователя. Регистрация определяется как первое
сообщение пользователя за всю историю, а не за окно расчёта, — иначе
«новичками» оказались бы все, кто просто писал в этот период.

**Глубина чтения.** Сообщений на два порядка меньше, чем реакций и подписок
(660 тысяч против 25 миллионов за месяц), поэтому сообщения читаются за всю
историю, а реакции и подписки — только за глубину расчёта.

**Расстояние между пользователями.** Считается между последними известными
координатами: непрерывного трека положения в данных нет, координаты
появляются только вместе с сообщениями.

**Ограничение объёма в рекомендациях.** За неделю набирается 5,6 миллиона пар
«пользователь — канал», что даёт около 1,6 миллиарда потенциальных сочетаний
внутри каналов. Поэтому `self-join` идёт по паре ключей `(channel_id, zone_id)`:
пользователи ближе километра гарантированно находятся в одном городе, так что
результат не меняется, а число сравниваемых комбинаций сокращается примерно
в 24 раза.

## Запуск

```bash
spark-submit --master yarn --deploy-mode cluster \
    --driver-cores 1 --driver-memory 2g \
    --executor-cores 2 --executor-memory 4g --num-executors 3 \
    --py-files geo_lib.py mart_users.py \
    2022-06-21 180 /user/master/data/geo/events \
    /user/s19239739/data/geo/geo.csv \
    /user/s19239739/data/analytics/mart_users
```

```bash
spark-submit --master yarn --deploy-mode cluster \
    --driver-cores 1 --driver-memory 2g \
    --executor-cores 2 --executor-memory 4g --num-executors 3 \
    --py-files geo_lib.py mart_zones.py \
    2022-05-31 30 /user/master/data/geo/events \
    /user/s19239739/data/geo/geo.csv \
    /user/s19239739/data/analytics/mart_zones
```

```bash
spark-submit --master yarn --deploy-mode cluster \
    --driver-cores 1 --driver-memory 2g \
    --executor-cores 2 --executor-memory 4g --num-executors 3 \
    --conf spark.sql.shuffle.partitions=400 \
    --py-files geo_lib.py mart_friends.py \
    2022-05-31 7 /user/master/data/geo/events \
    /user/s19239739/data/geo/geo.csv \
    /user/s19239739/data/analytics/mart_friends
```

Аргументы одинаковы у всех трёх джоб: дата расчёта, глубина в днях, путь к
событиям, путь к справочнику городов, выходной путь без даты.

## Автоматизация

DAG `geo_marts` запускается ежедневно (`@daily`) и считает три витрины
параллельно — между ними нет зависимостей, каждая читает Raw-слой
самостоятельно. Дата расчёта подставляется из макроса `{{ ds }}`,
скрипты лежат в `/lessons`, общий модуль передаётся через `py_files`.
